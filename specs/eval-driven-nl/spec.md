# NL 检索 · Eval-Driven 改造

> **状态**：🚧 实现中。
>
> 承接 `specs/nl-intent-retrieval/`（意图驱动检索）。那个 spec 把"检索层要听懂
> 风格"这件事做出来了，但**质量保证仍然是人工的**——改完靠人眼看一眼队列。本 spec
> 把它变成**可自动测量、可进 CI、可当门禁**的闭环。

## 做什么

把 NL 歌单的检索质量，从「改完靠肉眼判断」变成「**每次改动都被自动测量 + 不达标
就拦**」。

具体产出三层可运行的机制 + 一条流程规则：

| 层     | 名字         | 跑在哪           | 成本          | 判据                             |
| ------ | ------------ | ---------------- | ------------- | -------------------------------- |
| **L0** | 不变量门禁   | PR（`test.yml`） | 0 元 / 0 网络 | 与基线**无关**的不变量           |
| **L1** | 离线回放评测 | PR（`test.yml`） | 0 元 / 确定性 | 不变量 + 纯度**不低于**基线 N pt |
| **L2** | 真实链路评测 | 本机定时 / 手动  | 花钱          | 场景全量 + 报告快照              |
| **L3** | 评测驱动调参 | 本机             | 花钱          | sweep 数据选参数                 |

外加 **L4 流程固化**：改 NL 检索必须附评测对比数字。

## 为什么（现状差距）

2026-10-20 已交付 `npm run reco:eval:genre`（真实链路 · 5 场景 · 三指标）。它
**能抓 bug**——当场抓出 4 个真实问题（见下），但它**不是门禁**：

| 障碍                                      | 后果                                                            |
| ----------------------------------------- | --------------------------------------------------------------- |
| 要 DeepSeek key                           | CI 跑不了                                                       |
| 要平台登录态（QQ cookie / Spotify token） | CI **永远**跑不了                                               |
| 基线存 `packages/server/.storage/`        | **在 .gitignore 里** → 不在仓库，别人/CI 拿不到                 |
| 只有 5 个场景                             | intent 的表达能力（年代/语种/排除流派/参考曲目/冷门流派）没覆盖 |
| 没人会记得跑                              | 有尺子 ≠ 每次都量                                               |

### 2026-10-20 那 4 个 bug —— 为什么肉眼没抓到

| #   | bug                               | 肉眼看到的表现                               |
| --- | --------------------------------- | -------------------------------------------- |
| 1   | 超额要（overask 1.5x）让模型凑数  | 队列后半段风格不对（但"看起来有爵士"）       |
| 2   | **候选池缓存 key 不含构建参数**   | **代码改了，行为没变**（连续三轮评测都一样） |
| 3   | 池的来源交错让"相邻艺人"插队      | 队列里混进风格边缘的歌                       |
| 4   | `anchorLimit` 默认只深挖 3 个种子 | 池里凑不满 → 模型被迫挑风格外的补数          |

第 2 条尤其说明问题：**它不改变任何单次运行的结果，只改变"改动是否生效"**。
这类 bug 只有"每次改动都自动跑一遍评测"才抓得到。

## 仓库既有范式（照抄，不发明）

本 spec 的门禁形态沿用仓库已经跑起来的模式：

- **PR 门禁在 `test.yml`**（快）：问"你这次改的对不对"，**刻意不用基线快照**
  ——见 `scripts/coverage-diff-gate.js` 的注释：「它问的是"你这次写的代码有没有被
  跑到"，而不是"你这次写的代码比上次差多少"」。基线快照会持续产生 diff 噪音、
  且基线本身会腐烂。
- **重指标放每日定时**：`coverage.yml`（01:30）、`token-drift.yml`（01:00）——
  覆盖率是**仓库健康度**，不是 PR 质量门禁。
- **入库快照/预算文件**范式：`token-adoption-budget.json`、`token-drift-allowlist.json`。
- 门禁脚本要带 `--self-test`，且**主流程和自测调同一个函数**（自测里另写一份
  的话，判据改坏了自测测不出来——`coverage-diff-gate.js` 里踩过）。

## L0 — 不变量门禁（PR，0 成本）

把"风格纯度"翻译成一组**与基线无关**的硬性质。任一条不成立 → 这次改动破坏了
检索层 → 拦。

| 不变量                    | 判据                                   | 抓的 bug                    |
| ------------------------- | -------------------------------------- | --------------------------- |
| `no-radio-in-intent-mode` | intent 模式**不拉**平台私人 FM         | FM = 账号画像 = 污染源      |
| `all-seeds-searched`      | **每一个**种子艺人都被搜过             | #4 `anchorLimit` 截断       |
| `seed-artists-contribute` | 每个种子艺人至少贡献 1 首候选          | 种子无效（搜不到/被过滤光） |
| `seed-block-first`        | 种子艺人的候选**连续排在**其它候选之前 | #3 交错插队                 |
| `excluded-absent`         | 被排除的艺人不出现在候选里             | 排除项失效                  |
| `non-seed-ratio`          | 非种子艺人候选占比 ≤ 阈值              | 风格稀释（免费代理指标）    |
| `pool-not-empty`          | 候选非空                               | 检索崩了                    |

实现：`packages/server/src/reco/eval-invariants.ts`（纯函数）+ 一个测试文件直接
调用**真实的** `RecoService.buildPool`（fake provider，不出网）——**不另写一份
实现**（同 coverage 门禁的教训：自测必须测真身）。

## L1 — 离线回放评测（PR，确定性）

L0 只能抓"结构性"的破坏。要量化"风格纯度"，需要**消除两处不确定性**：

1. **平台搜索结果**（每次都不一样）→ 录制 fixture：`脚本` 把「艺人 → 平台搜索
   结果」录成 JSON 入库（`packages/server/src/reco/__fixtures__/search/`）。
2. **LLM 流派判定**（要花钱、要 token）→ **黄金集**（`__fixtures__/genre-golden.json`）：
   人工标注的「歌名-艺人 → 流派」对照，替代 LLM 判定。

于是 L1 变成**确定性**的：同样的 fixture + 同样的黄金集 → 同样的数字。

- 指标：检索层种子覆盖 + 黄金集判定下的池纯度 + 全部 L0 不变量
- 基线：**入库**（`specs/eval-driven-nl/baseline.json`）——这是"入库快照"范式，
  与 L0 的"不用基线"互补：L0 抓结构破坏，L1 抓纯度下降
- 门禁判据：**纯度不低于基线 N pt**（不是绝对相等——fixture 会随平台漂移，
  绝对相等必然假红）

### 诚实说明（L1 的局限）

- fixture 是**某一天**的平台结果 → 平台真实目录变了，fixture 不会跟着变 →
  L1 测的是"检索逻辑相对录制时是否退化"，不是"平台现状是否正确"
- L1 测的是**候选池**（检索层），不是最终队列（策展层还要 LLM 挑选）
- 所以 **L2 是必要的校准层**：L1 说"逻辑没退化"，L2 说"真实世界里也确实对"

## L2 — 真实链路评测（本机定时 / 手动）

现有 `npm run reco:eval:genre` 扩场景，覆盖 intent 的**全部表达能力**：

| 维度            | 场景                                  |
| --------------- | ------------------------------------- |
| 纯流派          | 来点儿爵士乐                          |
| 场景 + 流派     | 放点适合夜跑的电子乐                  |
| 流派 + 排除艺人 | 九十年代摇滚，排除周杰伦              |
| 参照型          | 像 Deadmau5 那种 prog house           |
| 中文民谣        | 周末慵懒的中文民谣                    |
| **年代**        | 八十年代合成器                        |
| **语种**        | 日式 city pop                         |
| **排除流派**    | 要摇滚但别要朋克                      |
| **参考曲目**    | 像《光辉岁月》那种                    |
| **冷门流派**    | 来点 afrobeat（测"没种子"的降级路径） |
| **混合流派**    | 爵士 + 电子（jazz fusion）            |
| **数量**        | 来 20 首                              |

**跑不进 CI**（要 key + 登录态）→ 定位是**本机定时**（用户机器上有凭据），
CI 只跑 L0/L1。跟 `coverage.yml` 一个思路：重活在有环境的地方跑。

### L2 实测结果（2026-10-23，12 场景 · 真实链路 · 库 1566 首）

| 指标             | 第 1 轮 | 第 2 轮 | 第 3 轮（最终） |
| ---------------- | ------- | ------- | --------------- |
| 检索层 种子覆盖  | 80.8%   | 77.8%   | **79.1%**       |
| 策展层 流派纯度  | 82.2%   | 83.3%   | **85.9%**       |
| 库污染（回音壁） | 12.5%   | 15.3%   | **11.0%**       |
| 主干污染         | 2.8%    | 2.1%    | **0.8%**        |
| 通过率           | 75%     | 83.3%   | **91.7%**       |

三轮的差别全是**评测驱动出来的修复**：库内去重放宽（种子块恢复）、种子数 4→6
（LLM 多给几位代表艺人）、判据口径统一（L2 与 L1 同用宽松纯度）。

**L2 抓出来的问题（离线评测没覆盖到的）**：

1. **库内去重把"用户想要的"滤光了** —— 中文民谣场景：用户库里本来就有大量
   陈粒/马頔/宋冬野/赵雷 → 库内去重把这些**正好是答案**的曲目全剔掉 → 种子块
   凑不满 12 首 → 模型从**漂移的相邻艺人**里挑（混进 4 首虞书欣/周深的流行
   OST，纯度 100% → 66.7%）。
   → 修：intent 模式下**种子艺人的库内曲目不算"重复"**。"别推荐我已有的"是
   **发现类**推荐的规矩；用户明确说"来点中文民谣"时，库里的民谣歌正是答案。
   （只放宽库内去重——"用户跳过过的""刚推荐过的"照旧排除，那是明确的负向信号。）
2. **离线评测复现不出这条路径** —— 离线 fixture 用的是**空库**，所以"库内去重
   饿死种子块"这条失败模式在离线层根本不存在。
   → 修：fixture 的每条结果带 `inLibrary` 标记 → 离线评测按同样的口径喂
   `library` 参数 → 这条路径现在**离线就能复现**（门禁能抓）。
3. **L2 与 L1 的 pass 判据不一致** —— L1 用宽松纯度（相邻子风格也算）、L2 用
   严格纯度，导致"八十年代合成器"离线通过、真实链路判红（严格 41.7% / 宽松
   100%——new wave、synth-pop 就是那个流派，判据太窄）。
   → 修：L2 也用宽松纯度，严格值同时报出来作对照。
4. **种子给太少**（"周末慵懒的中文民谣"）—— LLM 只给 4 位代表艺人，而每位种子在
   平台上能捞到的可用曲目**人均只有 2 首**（搜索结果里混着大量"歌名叫这个、
   歌手却是别人"的条目）→ 种子块只有 8 首 < 12 → 模型只能从**漂移的相邻艺人**
   里挑（混进 4 首虞书欣/周深的流行 OST，纯度 100% → 66.7%）。
   → 修：① 搜索 pageSize 10 → 20（provider 本来就取 30，是统一搜索层自己切的，
   成本≈0）；② prompt 要求 LLM 给 **4-6 位**代表艺人（原来 2-4 位）。

## L3 — 评测驱动调参

现在 `perArtistCap` / `overask` / `grouped` / `anchorLimit` / 邻居数这些参数是
"拍脑袋定 + 事后被 bug 教"。L3 让它们**由数据定**：

- **检索参数 sweep**（L1 跑，0 成本）：对每个参数组合跑一遍离线评测 → 出表 →
  选最优
- **prompt 参数 sweep**（L2 跑，花钱）：overask / prompt 措辞变体 → 同样出表
- 结论**写进本 spec**（每个参数配多少、为什么）——从此参数有据可查

### L3 实测结果（2026-10-23，12 场景 × 11 组）

| 组合                                          | 种子块纯度 | 队列纯度 | 种子块大小 | 不变量通过 | 评分      |
| --------------------------------------------- | ---------- | -------- | ---------- | ---------- | --------- |
| `perArtistCandidates=3`                       | 98.2%      | 84.7%    | 14.4       | 100%       | 0.945     |
| `maxPoolSize=30`                              | 97.6%      | 85.4%    | 19.8       | 100%       | 0.944     |
| `perArtistCap=6`                              | 98.2%      | 83.3%    | 28.7       | 100%       | 0.941     |
| **默认**（cap=4 / cand=6 / grouped / 邻居 1） | 97.6%      | 83.3%    | 20.3       | 100%       | **0.938** |
| `perArtistCandidates=10`                      | 97.5%      | 83.3%    | 21.2       | 91.7%      | 0.921     |
| `perArtistCap=3`                              | 97.0%      | 84.0%    | 15.8       | 91.7%      | 0.921     |
| `perArtistCap=2`                              | 96.8%      | 80.6%    | 11.3       | 41.7%      | 0.809     |
| `grouped=false`                               | 97.6%      | 82.6%    | 20.3       | **16.7%**  | 0.769     |
| `anchorLimit=3`                               | 99.0%      | 81.9%    | 12.0       | **0%**     | 0.741     |

**这张表最有价值的不是"最优是谁"，而是它把两个历史 bug 量化了**：

- `anchorLimit=3`（2026-10-20 那个 bug）→ **12/12 场景全破**
- `grouped=false`（交错合并那个 bug）→ **10/12 场景破**

也就是说：如果当初有这套门禁，那两个 bug 在**第一次改动时**就会被抓住，
而不是等到"人眼看出来了"才修。

### 结论（写进代码常量）

| 参数                  | 值           | 理由                                                                                                           |
| --------------------- | ------------ | -------------------------------------------------------------------------------------------------------------- |
| `perArtistCandidates` | 6            | 3 的评分高 0.007（噪声级），但种子块从 20.3 掉到 14.4 → 艺人多样性下降；10 反而在 1 个场景破门禁（池上限截断） |
| `perArtistCap`        | **4**        | 6 的评分只高 0.003（噪声级），但种子块从 20.3 涨到 28.7 → **一位歌手占满整批**的风险；4 更好                   |
| `grouped`             | **true**     | false 让 10/12 场景破门禁（种子块被从中间劈开）                                                                |
| `anchorLimit`         | **全部种子** | 3 让 12/12 场景破门禁                                                                                          |
| `relatedPerAnchor`    | **1**        | 纯度与默认持平，但**平台搜索少一半**（省延迟 + 少网易云 405 限流）                                             |
| `maxPoolSize`         | 60（默认）   | 30 的评分高 0.006（噪声级），但种子块更小；不值得动                                                            |

## L4 — 流程固化

- `CLAUDE.md` 架构约束加一条：**改 NL 检索必须先跑离线评测并把对比数字贴进
  PR 说明**；纯度下降就是回归，不接受"看起来还行"
- `lefthook.yml` pre-commit：改了 `packages/server/src/reco/**` 就跑离线评测
  （快、0 成本）——把检查前移到提交那一刻

### 已知残留（L1 与 L2 的差异）

L2 最终 11/12，剩下 `rock-no-punk`（"要摇滚但别要朋克"）：4 位种子（五月天/逃跑
计划/Beyond/Linkin Park）在平台上的**实际产出太少**（种子块只有 5 首 < 12）→ 模型
补了漂移的相邻艺人 → 纯度 60%。

**离线层复现不出这一半**：fixture 里那批艺人的产出更多（种子块 16）→ L1 绿。
这说明「种子在平台上的真实产出」是**活的、随时间变化**的量，录制时的快照不能
完全代表当下。L1 是"逻辑回归网"，L2 才是真实校准——两层都要在。

## 风险与局限

- **fixture 腐烂**：平台目录变了，fixture 不变 → L1 失去部分意义。缓解：L1 只判
  "不低于基线 N pt" + 定期重录（重录本身是 L2 的一部分）
- **黄金集覆盖不足**：黄金集没覆盖的歌算"未知"→ 纯度分母缩小 → 数字虚高。
  缓解：报告里同时给**黄金集覆盖率**，覆盖率低于阈值时**拒绝给结论**（fail loud）
- **离线 ≠ 真实**：L1 是逻辑回归网，L2 才是真实校准。两层都要在
- **门禁噪音**：如果 L0/L1 经常假红，人就会开始忽略它。缓解：判据宁少勿滥，
  每条不变量都要能指认它抓的是哪个真实 bug
- **成本**：L2 每次跑 ≈ 15 次 LLM 调用 + 几十次平台搜索；L3 的 prompt sweep 会翻倍。
  缓解：L2/L3 手动触发为主，不进定时
